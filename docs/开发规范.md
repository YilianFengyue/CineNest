# 开发规范

## 一、模块边界（最重要）

> **核心原则：一人一个功能域，从后端到前端全包，谁也不等谁。**

| 区域 | 谁能改 |
|------|--------|
| `cine_nest_app/lib/{http,utils,services,common,models,router}` | **共建区**：改动前群里说一声，避免冲突 |
| `cine_nest_app/lib/pages/feed/`、后端 `routers/feed.py`、`services/{agent,tmdb}`、`db/` | 成员 B |
| `cine_nest_app/lib/pages/player/`、后端 `routers/sources.py`、`services/video_engine/` | 成员 A |
| `cine_nest_app/lib/pages/creative/`、后端 `routers/{chat,poster}.py`、`services/{poster,news}` | 成员 C |
| `router/app_pages.dart` 的 getPages | 各自**只追加**自己的 GetPage，不动别人的 |

**不交叉修改别人的模块目录。** 需要别人配合的，走 API 契约或路由跳转。

## 二、分支约定
- `main`：可运行的稳定版，只合并联调通过的代码
- `feat/a-player`、`feat/b-feed`、`feat/c-creative`：各自开发分支
- 合并前先 `flutter analyze` 无 error；后端 `python -m py_compile` 无报错

## 三、功能验收（人工）
- 按《需求与计划书》F1–F12 的**验收标准**逐条人工走查
- 每个功能点完成 = 演示给另外两人看，对照验收清单打勾

## 四、模块文档与测试结果（强制）
每个模块开发完成，**必须**在 `docs/modules/<模块名>.md` 写清：
1. **功能说明**：实现了哪些功能点（F几）
2. **用法**：关键类/接口怎么调，给最小示例
3. **测试结果**：验收清单逐条结果 + 截图/接口返回样例

模板见 `docs/modules/_TEMPLATE.md`。目的：他人无需读全代码即可接手协作。

## 五、提交规范
- commit message：`[模块] 动词 + 内容`，如 `[feed] 帖子流首页 UI 完成`
- 不提交 `.env`、`*.db`、`build/`、`.dart_tool/`（已在 .gitignore）

## 六、代码风格
- Flutter：`flutter analyze` 零 error；命名跟随母版 PiliPlus 风格
- Python：函数/接口加中文 docstring，标注 `TODO(谁)` 便于追踪
